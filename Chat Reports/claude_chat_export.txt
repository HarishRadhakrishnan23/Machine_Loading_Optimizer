## What CP-SAT actually does

CP-SAT is a **constraint satisfaction + optimization solver**. You give it:
1. **Variables** — decisions to make
2. **Constraints** — hard rules that can never be violated
3. **Objective** — what to minimize

It then exhaustively searches (with smart pruning) for the assignment of variables that satisfies all constraints and minimizes the objective. It's not a heuristic — it proves optimality or gets as close as possible within a time limit.

---

## How our problem maps to it

### Variables

For every pending `(serial_no, operation_no)` pair, we create an **`IntervalVar`**:

```python
# Example: serial 25-25-01084, Op60 (Stem Boring), capable machines: MachineA, MachineB
task_A = model.NewOptionalIntervalVar(start_A, duration, end_A, is_on_A, "serial_01084_op60_machA")
task_B = model.NewOptionalIntervalVar(start_B, duration, end_B, is_on_B, "serial_01084_op60_machB")

# Exactly one machine must be chosen
model.AddExactlyOne([is_on_A, is_on_B])
```

`is_on_A` and `is_on_B` are boolean variables — the solver decides which one is `True`. That decision IS the machine allocation.

---

### Constraints

**1. Operation sequence (per serial):**
```python
# Op20 cannot start until Op10 finishes for the same serial
model.Add(start_op20 >= end_op10)
```

**2. No overlap per machine per shift:**
```python
# Machine A can't do two things at the same time
model.AddNoOverlap([all_interval_vars_assigned_to_machine_A])
```

**3. Capacity per machine per shift:**
```python
# Total time used on Machine A in Shift 1 on Date X ≤ available_time_min
model.Add(sum(durations on machine_A, shift_1, date_X) <= capacity_resolved[machine_A][shift_1][date_X])
```

**4. Setup time:**
```python
# If machine switches concatenation_key between two consecutive jobs, add setup_mins
# This is modelled by inserting a setup IntervalVar between the two tasks
```

---

### Objective

```python
model.Minimize(
    sum(urgency_weight[order] * max(0, completion_day[order] - pdd_day[order])
        for order in all_orders)
)
```

---

## How the "queue-depth" allocation emerges — no explicit queue logic needed

This is the key insight. We never write code that says "measure queue depth, redirect machine." The solver figures it out through the objective.

Here's the concrete scenario:

> Machine A can do **Op10 (Cone Oversize)** and **Op60 (Cone Finish)**.
> Op20 (PTA) is heavily backed up — 20 serials already waiting there.

**If the solver assigns Machine A to Op10:**
- More serials complete Op10 and join the Op20 queue
- Op20 queue grows even larger
- Those serials sit waiting at Op20 for many shifts
- Their completion dates push out → tardiness increases → **objective gets worse**

**If the solver assigns Machine A to Op60:**
- Op60 serials complete and move toward final operations
- Those orders finish closer to their PDD → tardiness decreases → **objective improves**

The solver tries both assignments, computes the objective value for each, and picks Op60. The queue-balancing behaviour is a **byproduct of minimizing weighted tardiness** — not an explicit rule we code.

---

## What the solver is actually doing under the hood

CP-SAT uses a combination of:
- **Constraint propagation** — eliminates impossible assignments early
- **Branch and bound** — splits the search space and prunes branches that can't improve the objective
- **SAT-based reasoning** — encodes constraints as boolean clauses for fast conflict detection

For a real shop floor with ~50–200 active serials across 10–15 machines over a 2-week horizon, CP-SAT typically finds a near-optimal solution in **seconds**, well within our 10-second limit for Engine 2.

---

## The one thing CP-SAT can't do automatically

Setup time sequencing within a shift — deciding **which concatenation_key batch to run first** on a machine to minimize total setup cost — is an ordering sub-problem (similar to TSP). We handle this by:
1. Letting CP-SAT decide which batches go on which machine+shift
2. Within a shift, sorting batches by `concatenation_key` (grouping same keys together) as a post-processing step before writing to `schedule_output`

This keeps the CP-SAT model tractable while still minimizing setup waste.
